# План виведення старого модуля з експлуатації

## Мета і межі

Мета — прибрати неоднозначний shared `formatDate()` з `lib/format.js` так,
щоб кожен споживач викликав formatter із назвою свого контракту. Дати у
даних лишаються `YYYY-MM-DD`; змінюється тільки відображення.

Цільові контракти:

- HTML-рахунок (HTTP і CLI через один renderer): `DD.MM.YYYY`;
- accounting CSV для «Облік-Плюс»: `MM/DD/YYYY`;
- текстові reminders: поточний `MM/DD/YYYY`.

Підхід — **branch by abstraction**: спочатку додати явні formatter-и поруч
зі старим API, мігрувати споживачів по одному, а `formatDate()` видалити
лише після того, як пошук і тести покажуть відсутність викликів. Жоден крок
не змінює формат одночасно для двох контрактів.

## Послідовність малих релізів

### 1. Зафіксувати контракти на рівні кінцевих виходів

- **Що змінюється:** без production-зміни перевірити й, за потреби, доповнити
  characterization tests для фінального HTML рахунку, фінального тексту
  reminder та повного рядка accounting CSV. Для CSV обов'язково лишити
  перевірку `DocDate` і `PayUntil`, отриманих через конфігураційний тип
  `Date`.
- **Чому можна випустити окремо:** це лише тестовий реліз; поведінка системи
  не змінюється, зате наступні релізи матимуть точні межі дозволеної зміни.
- **Захист:** `app/test/invoices.test.js` фіксує `DD.MM.YYYY`; 
  `app/test/reminders.test.js` — `03/12/2026`; `app/test/export.test.js` —
  `03/09/2026;03/23/2026`. Запускати повний `npm test`.

### 2. Додати паралельну явну абстракцію форматів дат

- **Що змінюється:** створити малий модуль, наприклад
  `lib/date-formats.js`, з трьома named exports:
  `formatInvoiceDate`, `formatReminderDate`, `formatAccountingDate`.
  Кожен приймає той самий `YYYY-MM-DD`/`Date` вхід і сам явно реалізує свій
  контракт. На цьому кроці жоден production consumer ще не перемикається.
- **Чому можна випустити окремо:** новий модуль не має callers, тому його
  додавання не змінює жодного виходу й дозволяє окремо перевірити API.
- **Захист:** unit-тести нового модуля для валідної, порожньої та невалідної
  дати; існуючий повний suite гарантує відсутність ненавмисної зміни виходів.

### 3. Мігрувати accounting CSV першим і прибрати неявний `Date` fallback

- **Що змінюється:** у `lib/export/accounting.js` замінити lookup
  `format['format' + col.type]` на явну таблицю renderer-ів цього export
  (наприклад, `Date: formatAccountingDate`, `Decimal: formatDecimal`,
  `Text: formatText`). Конфігурація як і раніше може перевпорядковувати
  колонки, але її тип `Date` матиме явно названий accounting formatter.
- **Чому можна випустити окремо:** CSV байт-в-байт лишається тим самим;
  змінюється лише внутрішня прив'язка formatter-а. Це ізолює найризикованіший
  зовнішній контракт до міграції людських виходів.
- **Захист:** `app/test/export.test.js` має порівнювати весь CSV, включно з
  CRLF і двома date-колонками. Додатково звірити
  `app/docs/integrations/oblik-plus.md`: `MM/DD/YYYY` є обов'язковим
  контрактом «Облік-Плюс».

### 4. Мігрувати reminders на явно названий formatter

- **Що змінюється:** у `lib/notifications/reminders.js` замінити
  `format.formatDate(invoice.due_at)` на `formatReminderDate(invoice.due_at)`.
  Текст, умови надсилання та outbox не змінювати.
- **Чому можна випустити окремо:** це один consumer; нова функція навмисно
  повертає наявний `MM/DD/YYYY`, отже користувацький текст не зміниться.
- **Захист:** `app/test/reminders.test.js` уже фіксує дату у тілі листа.
  Після релізу повний suite має залишитися зеленим без зміни expectation.

### 5. Мігрувати invoice renderer на `formatInvoiceDate`

- **Що змінюється:** у `lib/invoices/render.js` замінити поточне локальне
  перетворення результату shared formatter-а на прямий виклик
  `formatInvoiceDate`. HTTP route і `bin/render-invoice.js` не змінювати:
  вони вже спільно використовують цей renderer.
- **Чому можна випустити окремо:** це одна внутрішня заміна за збереження
  вже випущеного HTML-контракту `DD.MM.YYYY`; жоден інший consumer renderer-а
  не існує.
- **Захист:** `app/test/invoices.test.js` перевіряє фінальний renderer та
  HTTP endpoint. Та сама renderer-перевірка захищає CLI, бо CLI лише пише
  результат `renderInvoiceHtml` у stdout.

### 6. Вивести shared `formatDate()` з експлуатації

- **Що змінюється:** після міграцій виконати цільовий пошук прямих викликів,
  імпортів і динамічних lookup-ів. Якщо production callers відсутні,
  видалити `formatDate()` і пов'язаний date-specific JSDoc з
  `lib/format.js`; money/text/percent helpers лишаються. Оновити або видалити
  тільки тести старого API, що стали неактуальними.
- **Чому можна випустити окремо:** попередні релізи вже перенесли кожен
  контракт на власну абстракцію; видалення не повинно змінювати output.
- **Захист:** повний `npm test`, пошук `formatDate` у production-коді та
  три контрактні тести з кроку 1. Перед видаленням окремо перевірити
  `config/export-columns.json` і export renderer map, бо простий пошук за
  іменем функції не виявляє конфігураційно-динамічну залежність.

## Критерій завершення

У production-коді немає shared date formatter-а з неясною семантикою.
`formatInvoiceDate`, `formatReminderDate` і `formatAccountingDate` мають
явні назви, власні тести та незмінні контракти. Будь-яка майбутня зміна
формату починається з конкретного consumer-а, а не з глобального helper-а.
