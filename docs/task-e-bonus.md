# Task E (bonus) — Шлях 2: мутаційне тестування характеризаційних тестів

## Інструмент

Ручні мутації скриптом, **без нових залежностей**. Stryker не брали: він
очікує конфіг і раннер поверх npm-проєкту, а тут `node --test` і нуль
залежностей — ставити тулчейн заради 25 мутантів дорожче, ніж їх згенерувати.

Скрипт на кожного мутанта: копіює `app/` у `mktemp -d`, застосовує одну
текстову заміну, запускає `npm test`, рахує `^not ok`, викидає копію. Жодна
мутація не торкається робочої теки.

Мутували **і форматер, і споживачів, і контракт експорту** — бо саме в
споживачах ховався баг, якого тікет не бачив.

## Знахідка: мутант `getUTC*` → локальний час вижив, і це справжня дірка

Два тести, які мали б його вбити, були:

```js
assert.equal(format.formatDate('2026-03-09T23:59:59+03:00'), '03/09/2026');
```

Вони проходять і з мутантом — **бо ця машина стоїть в EEST (+0300)**. Перевірка
під різними TZ:

| TZ | поточний код | мутант (локальний час) |
|---|---|---|
| `UTC` | `09.03.2026` | `09.03.2026` |
| `Europe/Kyiv` | `09.03.2026` | `09.03.2026` |
| `America/New_York` | `09.03.2026` | **`08.03.2026`** |
| `Pacific/Honolulu` | `09.03.2026` | **`08.03.2026`** |

Тобто тест був **зелений через географію розробника**, а не через правильність
коду. На CI-раннері чи ноутбуці на захід від Гринвіча кожна дата в рахунку
з'їхала б на добу назад — і, що гірше, у `formatDate` теж, тобто рахунки
потрапили б у «Облік-Плюс» із чужою датою. Той самий мутант у `formatDate`
(дописаний після першого прогону) вижив рівно так само.

**Чим убили.** Один тест, який запускає обидва форматери в дочірньому процесі з
явним `TZ`, по п'яти зонах від `Pacific/Kiritimati` (+14) до `Pacific/Honolulu`
(−10):

```js
test('MUST-NOT-CHANGE both formatters are UTC-only, whatever the host timezone', ...)
```

Після додавання обидва мутанти — вбиті. Тест тепер означає те саме на будь-якій
машині.

## Мутант, що вижив законно

`formatDateUA`: заміна `if (!value) return ''` на `if (false) return ''`.

Не дірка в тестах, а **еквівалентний мутант**: другий guard,
`if (isNaN(d.getTime())) return ''`, перехоплює всі ті самі входи, бо `toDate`
клеїть `String(value).slice(0, 10) + 'T00:00:00Z'` і на будь-якому falsy дає
`Invalid Date`. Перевірено по всіх значеннях, на яких взагалі спрацьовує `!value`:

```
undefined  null  ''  0  -0  NaN  false  0n   -> 8 входів, 0 розбіжностей
```

Такого мутанта вбити тестом неможливо: поведінка не змінюється. Guard залишено
як є — він дублює перевірку, але це стиль самого `formatDate`, а прибирати його
означало б рефакторинг поза тікетом.

## Підсумок

- **24 з 24** нееквівалентних мутантів убито; 1 вижив і доведено еквівалентним.
- Мутаційне тестування знайшло те, чого не знайшло ні читання коду, ні
  перевірка 19 тверджень карти: **тест, зелений лише через часовий пояс
  машини**. Причому в тій самій функції, через яку дані йдуть у бухгалтерію.
- Найцінніший тест у сюїті — **golden master** експорту: він сам-один убив усі
  8 мутантів контракту, включно з мутацією JSON-конфіга, до якої жоден юніт-тест
  форматера не дотягується.
- Найцінніший **клас** мутанта — «повернути споживача на стару функцію»
  (`formatDateUA` → `formatDate` у `render.js`/`reminders.js`). Це рівно та
  регресія, яку хтось внесе через пів року, не читаючи
  [`app/AGENTS.md`](../app/AGENTS.md), і вона тепер ловиться.

Скрипт мутацій лежав у скретчпаді сесії і в репо не комітився (щоб не плодити
інструментів, яких ніхто не підтримує); відтворюється з таблиць вище — одна
текстова заміна на мутанта.
