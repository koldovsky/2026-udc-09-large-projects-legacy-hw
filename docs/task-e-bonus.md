# Task E (bonus) — оберіть ОДИН шлях

## Шлях 3 — план виведення старого модуля з експлуатації

План заміни спільного форматера на явні форматери для кожного споживача
(strangler fig), **кроками, кожен з яких безпечно випускати окремо**:

1. Створити нові специфічні функції у `lib/format.js`: `formatDateAccounting`, `formatDateInvoice`, та `formatDateReminder`. На цьому етапі `formatDateAccounting` делегує виклик до старого `formatDate`, а `formatDateInvoice` і `formatDateReminder` — до `formatDateUA`. Зареєструвати їх в `module.exports`.
2. У файлі `config/export-columns.json` замінити тип "Date" на "DateAccounting" (щоб він викликав `format['formatDateAccounting']`). Випустити зміни, переконавшись, що експорт для бухгалтерії працює без змін (формат MM/DD/YYYY).
3. Оновити файл `invoices/render.js` для використання нової спеціалізованої функції `formatDateInvoice` замість поточної `formatDateUA`. Випустити зміни, переконавшись, що формат рахунків (DD.MM.YYYY) збережено.
4. Оновити файл `notifications/reminders.js` для використання спеціалізованої функції `formatDateReminder` замість `formatDateUA`. Випустити зміни.
5. Після того, як усі споживачі перейшли на специфічні методи, функції `formatDate` та `formatDateUA` можна вбудувати (заінлайнити) безпосередньо у відповідні нові методи.
6. Видалити старі функції `formatDate` та `formatDateUA` з кодової бази, оскільки на них більше ніхто не посилається безпосередньо.

**Що на кожному кроці захищає від регресії:**
Наявність характеризаційних тестів (для HTML рахунків, нагадувань і CSV експорту), які фіксують очікуваний вихід для кожного зі споживачів. Поступовий (покроковий) перехід споживачів дозволяє звузити обсяг можливих помилок при кожному деплої, і тести забезпечують, що під час зміни точки виклику формат залишається незмінним.
