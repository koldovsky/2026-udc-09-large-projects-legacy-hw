# Task E (bonus) — обраний шлях 3

## Шлях 3 — план виведення старого модуля з експлуатації

План нижче замінює спільний date formatter на явний форматер для кожного споживача через **branch by abstraction**. Він охоплює тільки форматування дат; форматери грошей та інших значень не мігрують у цій роботі. Кожен крок можна випускати окремо, а чинні формати виходів мають залишатися незмінними.

1. **Зберегти baseline та контрактні тести.** Залишити golden master HTML рахунку, тексти upcoming/overdue нагадувань і повний рядок CSV «Облік-Плюс». Зафіксувати edge cases парсингу ISO-дати, `Date`, невалідних і порожніх значень. Цей тестовий реліз не змінює production-код.
2. **Додати явні форматери паралельно зі старим API.** Ввести `formatInvoiceDate`, `formatReminderDate` та `formatAccountingDate` (у відповідних модулях споживачів або невеликих доменних helper-модулях). Спершу вони делегують поточній реалізації, тому лише додають API і не змінюють виходи. Залишити `formatDate` як сумісний міст.
3. **Перевести HTML рахунку окремо.** `lib/invoices/render.js` переходить на `formatInvoiceDate`; прогнати його HTML-тести. Очікуваний вихід лишається `DD.MM.YYYY`; reminder та CSV на цьому кроці не змінюються.
4. **Перевести нагадування окремо.** `lib/notifications/reminders.js` переходить на `formatReminderDate`; перевірити upcoming і overdue текст та сформовані outbox-повідомлення. Очікуваний вихід лишається `DD.MM.YYYY`; HTML і CSV не змінюються.
5. **Закріпити окремий формат CSV.** `lib/export/accounting.js` використовує тільки `formatAccountingDate`, який явно повертає `MM/DD/YYYY` згідно з `app/docs/integrations/oblik-plus.md`. Перевірити незмінність golden master, заголовків, роздільника, CRLF і сум. Цей крок не змінює машинний контракт бухгалтерії.
6. **Прибрати спільний date API після перевірки посилань.** Пошуком по всьому `app/` підтвердити, що callers більше не імпортують `formatDate`/`formatDateUs`, потім видалити лише ці спільні date-функції та їхній parser, якщо той більше ніде не потрібен. Якщо `lib/format.js` має споживачів money/text/percent, лишити його для цих форматів; не перейменовувати і не мігрувати їх у цьому дифі. Якщо у репозиторії є зовнішній споживач, якого пошук не охоплює, залишити сумісні alias-и або виводити їх в окремому наступному релізі.

**Захист від регресій на кожному кроці:** запускати тести відповідного споживача і повний `npm test`; перед кожним переходом зберігати попередні golden outputs. Для двох клієнтських виходів очікування — `DD.MM.YYYY`; для бухгалтерського CSV очікування незмінне — `MM/DD/YYYY`. Релізити кроки 3–5 окремо, щоб зміна одного адаптера не маскувала регресію іншого.
