# Codebase map — `app/`

> Task A. The map was generated by the agent from the code, then checked by
> hand (section 3). Paths are relative to `app/`.

## 1. How the agent built the map

- Tool / model: Claude Code, Sonnet 5.5 (`claude-sonnet-5-5`).
- Prompt (condensed): "Map `app/`: entry points (HTTP, cron, CLI), modules and
  what they do, how data is stored, external integrations, where dates and money
  are formatted. Write it to `docs/codebase-map.md`."
- Navigation cost (approximate, from the context counter and my own tool log):
  - **11 tool calls**, all `Bash` (cat / grep / ls / `node -e`), no separate `Read` calls.
    Roughly 8 calls were used to build the map and 3 to verify it.
  - **About 24 files read in full** out of 61 files in `app/` (`server.js`,
    `lib/http/router.js`, `lib/store.js`, `lib/format.js`, `lib/export/accounting.js`,
    `lib/notifications/reminders.js`, `lib/invoices/{index,render}.js`, all 6 `bin/*`,
    `package.json`, `config/*`, and the three legacy docs).
  - **About 17 more files: only the first 20-30 lines** (the header comment) of
    `lib/{discounts,audit,catalog,customers,orders,payments,reports}/*`. Their
    descriptions below come from those headers and from grep, not from reading the logic.
  - The remaining files (test files, `data/*`, `routes.js` bodies, `lines.js`,
    `validate.js`, `search.js`) were only searched with grep or `wc`.
  - **About 79k tokens** in total, from the drop in the session's `total_tokens`
    counter (15,000,000 to about 14,921,000). That includes the system prompt and
    my own output, so treat it as an upper bound for navigation alone.
- Read everything or searched? **Searched.** The order was: `ls` of the tree, then
  entry points, then `grep` for `require('./`, routes, `process.env` and network calls,
  then header comments, then the few files that carry the date and money logic.
  I read the **old docs (`app/README.md`, `docs/ARCHITECTURE.md`,

  The map below is therefore built from the code, not from the docs. That is why

### Data

- Every collection is a file `data/<name>.json` (a JSON array). `lib/store.js` loads it
  lazily, caches it in memory and rewrites the **whole file** on `save()`.
  There is no database, no locking, no transactions. Callers must call `store.save()`
  themselves, and some paths do not (3.11).
- Collections present: `customers` (12), `orders` (36), `invoices` (36), `payments` (6),
  `products` (20), `stock` (20), `price_history` (38). The payment import also uses
  `credits` and `unmatched` (created on first write).
- Also on disk: `out/export/` (CSV), `out/mail/` (mails), `out/audit.log` and
  `out/audit-archive/` (not in the repo, created at run time).
- **Dates** are stored as `YYYY-MM-DD` strings. Audit timestamps are full ISO UTC.
- **Money** is an integer number of kopecks (`*_kopecks` fields). Price import is the
  only place that accepts hryvnias, and it converts.
- **Where dates and money are formatted** (several places, on purpose or not):
  - `lib/format.js`: `formatDate` returns `MM/DD/YYYY` (not ISO); `formatMoney` returns
    `1 234,50 грн`; `formatDecimal` returns `1234.50`.
  - `lib/reports/dates.js` and `lib/reports/table.js` (`fmtAmount`, `1 234,50` without currency).
  - `bin/import-statement.js` (`fmtAmount`, `1234.50`).
  - Local ISO date helpers in `lib/orders`, `lib/customers`, `lib/invoices` (`addDays`),
    `lib/discounts`, `lib/audit`, `lib/catalog/price-import.js`, `lib/payments/statement.js`.
  - The export CSV is rendered by `lib/format.js` through `config/export-columns.json`
    (the `type` field is mapped to `format<Type>`).

### External integrations

- **Accounting (Облік-Плюс)**: the nightly CSV, `;` separator, CRLF, UTF-8, dates
  `MM/DD/YYYY`, amounts `1234.50`. The consumer skips rows with a different date format
  silently (per `docs/integrations/oblik-plus.md`; this part cannot be checked from the code).
  The first lines of the real file confirm the format (3.10).
- **Mail**: no SMTP in this code. Reminders are files in `out/mail/`; the old SMTP relay
  picks them up (from a comment).
- **Bank**: a KB-2 fixed-width statement, delivered through an SFTP bridge or posted to
  `POST /api/payments/import`.
- **Reverse proxy / LDAP**: supplies `x-staff-id` (from a comment).
- **Dead**: `pdf-render` HTTP service, MongoDB.

## 4. Conclusion

**Where the map was wrong or misleading**

- I did not copy the old docs into the map, because I built it from the code first and
  opened the docs last. Section 3 shows that doing it the other way round would have been
  expensive: `docs/ARCHITECTURE.md` is wrong on Express, MongoDB, Handlebars templates,
  PDF, SMTP, the port (3000), the module list, and the dates claim. Rows 1, 3-7, 9 and 11
  are all cases where a map built from that doc would have been wrong.
- Two things I got right only because I grepped instead of trusting names or comments:
  `lib/discounts` and `lib/audit` look like normal modules (tests, routes, a feature flag),
  but the app never calls them on the write path (rows 12 and 13).
- **The one thing in the map I cannot stand behind is the cron schedule** (row 17). It is
  all comments, the crontab is outside the repo.
- Where the map says what a module "does" for `catalog`, `customers`, `orders`, `payments`
  and `reports`, I read the header comment only (section 1). I expect that to be right, but
  I did not verify it by reading the logic, and the checks above do not cover it.

**Why I think these were the riskiest claims**

- The old docs are the biggest risk, because they are confidently wrong. Rows 1, 3-7, 9, 11
  check each of their claims.
- Dates and money formatting is where the next ticket will hurt. `formatDate` says "ISO"
  and prints `MM/DD/YYYY`, the export depends on it, and the consumer fails silently
  (`docs/integrations/oblik-plus.md`). I checked the real bytes of the export (row 10),
  not just the code.
- Rows 13 and 14 are not in any doc. They came out of grep, and they are the kind of
  surprise a map should contain.

**What I did not check**

- I ran the real server and the export, but not `send-reminders`, `monthly-report` or the
  payment import.
- Row 14 is a reading of the code. A one-line run of `bin/send-reminders.js` on a date with
  an overdue invoice, twice in a row, would confirm it.
- This verification was done by the same agent that wrote the map. A human reviewer should
  rerun at least rows 2, 9 and 10, each is one command.
