# Карта кодової бази — `app/`

## 1. Як агент будував карту

- **Інструмент / модель:** Codex, GPT-5.6 Terra (Medium).
- **Промпт (стисло):** дослідити вихідний код `app/`, визначити HTTP, cron і CLI точки входу, основні модулі та їх взаємодію, зберігання даних, зовнішні інтеграції, форматування дат і грошей. Навести посилання на код і статистику навігації. Використовувати цільовий пошук, не змінювати файли репозиторію. Результат надати українською.
- **Вартість навігації:** 23 унікальні прочитані файли, 6 викликів інструментів (за звітом агента). Кількість токенів недоступна.
- **Стратегія:** агент використовував `rg` і вибіркове читання ключових файлів, а не послідовне читання всього репозиторію.

## 2. Карта (те, що видав агент, з вашими правками)

### Точки входу

| Точка входу | Що запускає | Файл |
|---|---|---|
| HTTP | Node HTTP-сервер, сім наборів маршрутів | `app/server.js` |
| Cron | Щонічний бухгалтерський CSV-експорт (02:30) | `app/bin/nightly-export.js` |
| Cron | Формування нагадувань у робочі дні (09:00) | `app/bin/send-reminders.js` |
| Cron | Місячний звіт першого числа (07:00) | `app/bin/monthly-report.js` |
| CLI | HTML-рендеринг рахунків | `app/bin/render-invoice.js` |
| CLI | Імпорт банківських виписок | `app/bin/import-statement.js` |
| CLI | Разове виправлення дублікатів клієнтів | `app/bin/fix-2022-duplicate-customers.js` |
| Legacy CLI | Міграція MongoDB dump | `app/lib/legacy/mongo-migrate.js` |

Розклад cron наведено за коментарями у вихідному коді. Фактичну конфігурацію планувальника на сервері не перевірено.

### Модулі

| Модуль | Відповідальність | Живий / мертвий |
|---|---|---|
| `lib/http/` | HTTP-маршрутизація, JSON, контекст користувача | Живий |
| `lib/store.js` | Читання, кешування та збереження JSON-колекцій | Живий |
| `lib/customers/` | Клієнти, валідація, пошук, деактивація | Живий |
| `lib/catalog/` | Товари, ціни, залишки, історія цін | Живий |
| `lib/orders/` | Замовлення та їхні статуси | Живий |
| `lib/invoices/` | Створення рахунків, ПДВ, HTML-рендеринг | Живий |
| `lib/payments/` | Імпорт і зіставлення платежів | Живий |
| `lib/reports/` | Виручка, ПДВ, заборгованість, топ-клієнти | Живий |
| `lib/notifications/` | Підготовка нагадувань | Живий |
| `lib/export/` | Бухгалтерський CSV-експорт | Живий |
| `lib/audit/` | Журнал аудиту та архівація | Живий |
| `lib/discounts/` | Розрахунок знижок | Наявний, без окремих HTTP-маршрутів |
| `lib/legacy/pdf-client.js` | Старий клієнт PDF-сервісу | Не використовується в перевіреному активному рендерингу |
| `lib/legacy/mongo-migrate.js` | Міграція старих MongoDB-даних | Legacy CLI |

Основний потік: HTTP → маршрутизатор → доменний модуль → `store` → JSON-файли. Модулі замовлень, рахунків, платежів і звітності взаємодіють через спільні колекції.

### Дані

Основні дані зберігаються в JSON-файлах каталогу `app/data/`: клієнти, замовлення, рахунки, платежі, товари, залишки та історія цін.

`lib/store.js` завантажує колекції за потреби, кешує їх у пам'яті процесу та записує через `save()`. Окремої СУБД в описаному механізмі немає.

Дати доменних записів представлені рядками `YYYY-MM-DD`, грошові значення — цілими копійками.

Спільний модуль `lib/format.js` містить:

- `formatDate()` — відображення дати як `MM/DD/YYYY`.
- `formatMoney()` — гривні з пробілами між тисячами та комою перед копійками.
- `formatDecimal()` — десятковий формат для машинного обміну.
- `formatPercent()` — форматування відсотків.

Частина модулів має власну логіку форматування. Це важливо враховувати під час змін, оскільки не всі формати централізовані.

Журнал аудиту зберігається в `out/audit.log`, архіви — в `out/audit-archive/`.

### Зовнішні інтеграції

- **Бухгалтерська система:** отримує CSV-файли, які формує `lib/export/accounting.js` відповідно до `config/export-columns.json`. Файли записуються до `out/export`.
- **Нагадування:** скрипт `send-reminders.js` створює повідомлення у файловому каталозі `out/mail`. Безпосереднє SMTP-відправлення в перевіреному коді відсутнє.
- **Reverse proxy:** передає ідентифікатор співробітника через HTTP-заголовок `x-staff-id`. Маршрутизатор вимагає його для `/api/`.
- **Банківські виписки:** імпортуються з файлів через CLI.
- **Legacy PDF-сервіс:** клієнт існує, але активний маршрут рахунків використовує HTML-рендеринг замість нього.

## 4. Висновок

Із 11 перевірених тверджень 10 підтверджено вихідним кодом, одне залишилося непідтвердженим повністю.

Найважливіша знахідка — розбіжність між документацією та реалізацією `formatDate()`. JSDoc описує результат як ISO, але функція повертає `MM/DD/YYYY`. Агент правильно визначив фактичну поведінку, не покладаючись лише на коментар.

Друге ризиковане твердження стосується cron. Коментар повідомляє про вимкнення автоматичного імпорту виписок, проте конфігурація планувальника відсутня в репозиторії. Без доступу до сервера підтвердити це неможливо.

Найризикованішими для перевірки обрано твердження про застарілі компоненти (PDF-клієнт, cron), зовнішні інтеграції (SMTP, CSV), форматування дат і грошей та збереження даних. Ці ділянки особливо вразливі до розбіжностей між документацією та реальною реалізацією: старий код може залишатися в репозиторії, але вже не використовуватися, а зміни форматування можуть порушити роботу зовнішніх систем. Саме тому перевіряли фактичні виклики функцій, імпорти, операції запису та конфігурацію, а не лише коментарі. Такий підхід дозволив виявити застарілий JSDoc для `formatDate()` і встановити, що вимкнення cron неможливо незалежно підтвердити.

**Висновок:** карта агента виявилася корисною та переважно точною, але її слід розглядати як початкову гіпотезу. Ручна перевірка дозволила відокремити підтверджені факти від тверджень, заснованих лише на коментарях або неповній інформації.
