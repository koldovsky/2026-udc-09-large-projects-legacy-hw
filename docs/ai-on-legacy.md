# Де агент помилявся на legacy-коді

> Task D, частина 1.

## Основний прогін: помилок щодо legacy-коду не було

Основний агент — Claude Code, Opus 5.5 (Tasks A–C). На жодному з тверджень про
`app/` він не помилився. Найризикованіше перевірено:

- **Тези зі старої документації.** `app/docs/ARCHITECTURE.md` (2019) агент
  читав **останнім** і кожну тезу звіряв з кодом. Express, MongoDB, порт 3000,
  `lib/export/csv.js` і «форматування лише в шаблонах» позначено як ❌
  (`docs/codebase-map.md`, § 3, № 1–6).
- **Прихований споживач.** Його знайшли пошуком за `require('../format')`, а не
  за іменем `formatDate` (`docs/impact.md`, § 3). Мутацією `formatDate` в
  пам'яті підтвердили, що CSV справді йде через цю функцію.
- **Вихід для «Облік-Плюс».** Після зміни він байт у байт збігається з еталоном
  до зміни (`cmp`), а еталон `oblik.csv` не перегенеровувався
  (`docs/impact.md`, § 5).

Агент помилявся лише в процесі, не в розумінні коду. Для протоколу:

- Він стверджував, що контрольний прогін Task D «вже закомічено». Насправді
  коміти `09a09ad` і `7ada5a0` зробив автор курсу, і вони змінюють умову
  завдання. Помилку помітив сам агент, коли перед плануванням Task D подивився
  `git show --stat`: агент вивів висновок із самих повідомлень комітів.
- В одному з перших запусків перевірки в Task C команда `cd app` впала, бо
  shell уже був у `app/`. Перевірки відпрацювали на незмінених файлах і надрукували
  «успіх», тобто нічого не довели. Агент помітив `no such file or directory` і
  перезапустив їх; у результатах фігурує лише другий прогін.

Оскільки помилок щодо legacy-коду не було, нижче — контрольний прогін.

## Контрольний прогін

- **Чистий клон:** так.
  `git clone` цього репо → `git checkout 7ada5a0` (стан курсу до моєї роботи)
  → видалено кореневі `README.md`, `AGENTS.md`, `CLAUDE.md`, `.coderabbit.yaml`,
  `.github/`, `docs/`. `app/README.md` і `app/docs/` лишились. Засіяні тести на
  старті: `106 pass`.
- **Інструмент і модель:** Claude Code 2.1.285 headless (`claude -p`),
  **`claude-haiku-4-5`** — найшвидша й найдешевша модель, доступна моєму ключу.
  Інструменти: Read/Grep/Glob/Edit/Write, `npm test`, `node`, `grep`, `ls`,
  `cat`, `git diff`, `git status`.
- **Промпт:** лише тікет — вміст `materials/ticket-BILL-482.md` дослівно, через
  stdin, без жодних доповнень.
- **Вартість:** 22 ходи, 21 виклик інструментів, 58 с, $0.28 (≈1,25 млн
  токенів, майже все — кеш-читання).
- **Що змінила:**

  ```
   app/lib/format.js         | 4 ++--
   app/test/invoices.test.js | 4 ++--
  ```

  ```diff
  -  return pad(d.getUTCMonth() + 1) + '/' + pad(d.getUTCDate()) + '/' + d.getUTCFullYear();
  +  return pad(d.getUTCDate()) + '.' + pad(d.getUTCMonth() + 1) + '.' + d.getUTCFullYear();
  ```

  Тобто змінила **спільний** `formatDate` (і JSDoc на «Ukrainian format»), а в
  засіяному `invoices.test.js:41-42` оновила очікування. Прочитала лише
  `format.js`, `invoices/render.js`, `notifications/reminders.js` і три тести.
  `export/accounting.js`, `config/export-columns.json` і
  `app/docs/integrations/oblik-plus.md` не відкривала. Потім спробувала
  закомітити (`git add -A && git commit`), але `git commit` не було в дозволених
  інструментах, тож зміни лишились незакоміченими.
- **Що сказала про результат:**
  > «All 106 tests pass, including the invoice and reminder tests. The shared
  > `formatDate` function used by both invoice rendering and reminder emails now
  > displays dates in the unambiguous Ukrainian format.»

  «Used by both invoice rendering and reminder emails» — неповно: третій
  споживач, CSV для бухгалтерії, у її картині відсутній.
- **Чи змінився вихід, який читає інша система?** **Так.** Перевірено двома
  способами:
  1. `buildAccountingFile` по `data/` у клоні дав
     `INV-2026-00001;01.03.2026;15.03.2026;…` замість `03/01/2026;03/15/2026`.
     `cmp` з `app/test/golden/oblik.csv` (еталон із `9f2b29e`) показав
     розбіжність, і в **усіх 36 рядках** даних змінено `DocDate`/`PayUntil`.
     За `app/docs/integrations/oblik-plus.md` «Облік-Плюс» такі рядки мовчки
     пропускає, тож наступної ночі в облік не потрапив би жоден рахунок.
  2. Мої характеризаційні тести з Task B, скопійовані в тимчасову копію клону:
     `not ok` для всіх трьох. Два з них, клієнтські, червоніють очікувано, а
     `Oblik Plus accounting CSV, byte for byte` — це регресія.
- **Тести:** засіяні — **106 / 106 зелені**, жоден засіяний тест формат CSV не
  перевіряє. Мої характеризаційні — 0 / 3.
- **Висновок.** Модель зробила рівно те, що підказує тікет («здається, це одна
  функція»). Вона знайшла функцію пошуком за назвою, побачила двох прямих
  споживачів і на цьому зупинилась. Зелені засіяні тести дали їй хибну
  впевненість. Основний прогін відрізнявся трьома речами:
  1. Шукав, **хто імпортує модуль**, а не хто викликає функцію. Так знайшовся
     `format['format' + col.type]`.
  2. Прочитав `app/docs/integrations/oblik-plus.md` — єдиний актуальний документ
     у `app/docs/`, де прямо описано контракт `MM/DD/YYYY` і «тихе» пропускання
     рядків.
  3. **До** зміни зафіксував вихід CSV golden-тестом, який червоніє на такій
     правці.

  Цього знання не видно ні з коду, ні з тестів. Тому воно записане в
  `app/AGENTS.md`.
