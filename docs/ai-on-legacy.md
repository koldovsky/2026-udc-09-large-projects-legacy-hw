## Випадок 1 — «Жоден тест не фіксує формат дати», доведено хибним `grep`

- **Що просили:** Task A. Скласти карту `app/` і перевірити ≥10 її тверджень доказами.
- **Що агент сказав або зробив:** у `docs/codebase-map.md`, п. 4, записав
  «Жоден тест не фіксує формат дати ні в рахунку, ні в листі, ні в CSV» з
  позначкою ✅. Доказом був `grep "\d{2}/\d{2}/\d{4}" app/test`, який знайшов
  лише `orders/routes.test.js:49`.
- **Як помітили:** у Task B агент відкрив `app/test/invoices.test.js`, щоб
  скопіювати стиль тестів, і побачив на рядках 41–42
  `assert.match(html, /Дата: <b>03\/09\/2026<\/b>/)`. Тест фіксує саме те, чого
  «не існувало».
- **Чому він так вирішив:** у регулярному виразі слеші екрановані (`03\/09\/2026`),
  тому шаблон `\d{2}/\d{2}/` цей рядок не знаходить. Агент прийняв **порожній
  результат пошуку за доказ відсутності** і не спробував інший шаблон. У legacy-коді
  літерал часто пишуть не так, як шукаєш: в екранованому вигляді, в регулярці,
  частинами.
- **Як виправили:** повторний пошук з `\\?` перед слешами. П. 4 карти виправлено
  на ❌ з поясненням. Тест `invoices.test.js:41-42` внесено в `docs/impact.md` як
  споживача №4. У Task C він почервонів, як і передбачено, і його очікування
  оновлено.
- **Перевірте самі:**

  ```bash
  # пошук агента в Task A: invoices.test.js НЕ знаходить, лише orders/routes.test.js:49
  git grep -nE '[0-9]{2}/[0-9]{2}/[0-9]{4}' 7ada5a0 -- app/test
  # з урахуванням екранування \/ : знаходить ще invoices.test.js:41 і :42
  git grep -nE '[0-9]{2}\\?/[0-9]{2}\\?/[0-9]{4}' 7ada5a0 -- app/test
  ```

  Результат перевірки людиною: ☑ **підтверджую.** Перша команда знайшла лише
  `orders/routes.test.js:49`, друга ще й `invoices.test.js:41-42`
  (`03\/09\/2026`, `03\/23\/2026`). Запускав у cmd з подвійними лапками і
  `GIT_PAGER=cat`.

## Випадок 2 — Контракт «Облік-Плюс» «перевірено» по колу

- **Що просили:** Task A. Перевірити твердження карти, насамперед ті, що взяті зі
  старої документації.
- **Що агент сказав або зробив:** у `docs/codebase-map.md`, п. 5, записав
  «„Облік-Плюс“ очікує дату саме `MM/DD/YYYY`» з ✅. Доказ: «`oblik-plus.md:23`
  збігається з виходом коду». На цьому твердженні тримається все рішення Task C.
- **Як помітили:** під час самоперевірки для Task D. Агент шукав, на яких
  неперевірених джерелах тримаються його висновки. `git grep "MM/DD"` показав, що
  вимога записана **в одному місці**, у документі 2021 року. Ні зразка
  прийнятого файлу, ні тесту з боку «Облік-Плюс», ні конфігу їхнього імпорту в
  репо немає. Людина цю помилку не помічала.
- **Чому він так вирішив:** `ARCHITECTURE.md` агент щойно впіймав на брехні, а
  `oblik-plus.md` виглядав правдоподібно: новіший, з історією інциденту, і код
  йому відповідає. Але «документ збігається з кодом» не доводить, що так хоче
  зовнішня система. Обидва могли виникнути з одного припущення. Один legacy-документ
  агент перевіряв, а іншому повірив, бо той **зручно пояснював** знайдене.
- **Як виправили:** п. 5 карти перепозначено як ⚠️ «неперевірюване з репо». У
  `app/AGENTS.md` записано, що вимогу треба підтверджувати в бухгалтерії
  (Марина, вн. 214, за тим самим документом). Наслідків для коду немає: у Task C
  обрано варіант, за якого CSV **не змінився ні на байт**
  (`git diff e466473 HEAD -- app/test/characterization/golden/oblik-export.csv`
  порожній). Отже, хоч би що насправді приймав «Облік-Плюс», для нього нічого не
  змінилось. Невизначеність стала нешкідливою, але впевненість у звіті була
  незаслуженою.
- **Перевірте самі:**

  ```bash
  # єдине джерело вимоги MM/DD/YYYY у стартовому коді — один рядок документа
  git grep -n "MM/DD" 7ada5a0 -- app
  # CSV-еталон між комітом тестів і комітом зміни не змінився (порожній вивід)
  git diff e466473 HEAD -- app/test/characterization/golden/oblik-export.csv
  ```

  Результат перевірки людиною: ☑ **підтверджую.** `git grep "MM/DD"` у стартовому
  коді знаходить рівно один рядок, `app/docs/integrations/oblik-plus.md:23`.
  `git diff e466473 HEAD` по CSV-еталону порожній.

## Випадок 3 — Розклади cron з коментарів записано як факти

- **Що просили:** Task A. Точки входу (HTTP, **cron**, CLI).
- **Що агент сказав або зробив:** у таблиці точок входу `docs/codebase-map.md`
  записав як факти: «cron 02:30 — нічний CSV», «cron 09:00 робочі дні —
  нагадування», «cron 07:00 1-го числа — звіт», «„Облік-Плюс“ забирає о 06:00»,
  «SMTP-relay забирає з `out/mail`». Позначку «за коментарем» має лише рядок
  03:10.
- **Як помітили:** під час самоперевірки для Task D. Агент шукав джерело
  розкладів: `git ls-files | grep -i cron` нічого не повертає. Файлу
  `ops/crontab`, на який посилаються коментарі («see ops/crontab on the old box»),
  у репо немає. Усе про розклад і про те, хто забирає файли, — це **тільки
  коментарі** в `bin/*.js`. Людина цю помилку не помічала.
- **Чому він так вирішив:** коментарі в коді здаються надійнішими за окремі
  документи, бо «лежать поруч із кодом». Але це та сама стара документація, тільки
  в іншому файлі. Цей репо вже показав два брехливі коментарі (`router.js:92-93`,
  `audit/routes.js:3`), і агент їх упіймав, а коментарям про cron повірив без
  перевірки. Окремий доказ: `bin/import-statement.js:8-10` прямо каже, що його
  cron **вимкнули у 2022**. Тобто розклади в коментарях застарівають.
- **Як виправили:** під таблицею точок входу в карті додано ⚠️-примітку:
  розклади й поведінка зовнішніх систем відомі лише з коментарів і не перевірені.
  У `app/AGENTS.md` записано, що перед будь-якою зміною, яка залежить від часу
  запуску (наприклад, `today` за UTC у `bin/nightly-export.js:12`), розклад треба
  підтвердити в експлуатації.
- **Перевірте самі:**

  ```bash
  # crontab у репо немає (порожній вивід)
  git ls-files | grep -i cron
  # усе, що відомо про розклад, — коментарі
  git grep -n "Cron:\|cron on the old box\|turned cron back" -- app/bin app/lib
  ```

  Результат перевірки людиною: ☑ **підтверджую.** `git ls-files | grep -i cron`
  нічого не знаходить. `git grep` знаходить рівно 5 коментарів:
  `import-statement.js:10` («nobody turned cron back on»), `monthly-report.js:9`,
  `nightly-export.js:3`, `send-reminders.js:3`, `audit/retention.js:5`. Інших
  джерел розкладу в репо немає.

## Дрібні промахи з інструментами (не про legacy-код, для повноти)

- **Вигадана поведінка `node --test`.** Агент написав у шапці тесту команду
  `UPDATE_GOLDEN=1 node --test test/characterization`, не перевіривши її. Node
  сприймає теку як файл і падає з невиразним `test failed`. Помітили з першого ж
  прогону і виправили на шлях до файлу.
- **Оцінка токенів.** У Task A агент записав «≈58 тис. токенів» як вартість
  навігації, оцінивши її за власним лічильником контексту. Лічильник інструмента
  показав `Out: 103.0k`, тож оцінку замінено на дані інструмента з поясненням,
  як їх розподілено.
- **Середовище.** Агент запустив `git`, не перевіривши, чи він є в PATH (його там
  немає), і передав JS-код у `node -e`, а PowerShell обрізав у ньому лапки. Обидва
  промахи одразу видно з помилки.

## Що з цього виносимо

1. **Порожній результат пошуку — не доказ.** Перед твердженням «нікого / ніде
   немає» потрібен другий, інакше сформульований пошук: інше екранування,
   динамічні імена (`format['format' + type]`), конфіги.
2. **Документ, що збігається з кодом, не доводить контракт.** Вимоги зовнішньої
   системи з репо не перевіряються, і так треба прямо писати.
3. **Коментар у коді теж стара документація.** Він має такий самий статус, як
   `app/docs/`: його треба перевіряти.
